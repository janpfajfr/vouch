⏺ Here's what's in this branch/project.

  you-shall-not-add (alias safe-add)

  A dependency-governance gate for Node.js projects and coding agents. The pitch
   is in the README's tagline: "The tool does not prevent the bypass. It makes 
  the bypass impossible to hide."

  Instead of pnpm add some-package, you run npx you-shall-not-add some-package.
  It reviews the package, suggests alternatives, then installs and records the
  decision in a committed ledger. In CI, you-shall-not-add check fails any PR
  that added a dependency without a ledger entry.

  Core concept

  - Provenance + enforcement, not scanning. Explicitly not a CVE/typosquat
  scanner (defers that to npq/Socket).
  - Approval ledger at .security/dependency-approvals.json, committed to the
  repo.
  - --force-with-reason is attribution, not authorization — a high-risk dep
  still only passes CI once a human adds approvedBy to the ledger entry.

  Code layout (src/, ~480 LOC, zero runtime dependencies, Node 18+ built-ins 
  only)

⏺ Code read. Two things that shape the design:

  1. runCheck is pure and synchronous, and its CheckViolation[] is what fails
  CI. Since CVE drift should warn, never fail, it must NOT flow through
  CheckViolation — it needs a separate warnings channel and an async step.
  2. registry.ts is deliberately fail-closed (offline → throw → block). CVE
  re-query must be the opposite: fail-open (offline → "couldn't verify" warning,
   never block). Different semantics → it belongs in its own module, not bolted
  onto registry.ts.

⏺ Recommended approach

  New src/advisories.ts module (mirrors registry.ts's shape, but fail-open) + an
   optional cve field on the ledger entry + a new refresh command + a separate
  warnings pass in check. I considered folding it into registry.ts (rejected —
  mixes fail-closed and fail-open semantics in one file) and a stale-flag-only
  design (you already ruled that out).

  Here's the design. I'll go section by section — tell me where to adjust.

  ---
  1. Data: extend LedgerEntry (backward-compatible)

  A new optional cve field, so existing ledgers stay valid:

  interface CveSnapshot {
    advisories: { id: string; severity: "low"|"moderate"|"high"|"critical" }[];
   // id = GHSA id (fallback npm id)
    highestSeverity: "none"|"low"|"moderate"|"high"|"critical";
    queriedAt: string;   // ISO timestamp
  }
  // LedgerEntry gains:  cve?: CveSnapshot;
  advisories sorted by id for stable git diffs. Queried against the entry's
  approvedVersion (provenance: "the version you approved now has a CVE").

  2. New module src/advisories.ts — fail-open

  interface AdvisoryClient {
    // returns name -> advisories, or null for "couldn't verify" (offline/error)
    fetchBulk(pkgVersions: Record<string, string[]>): Promise<Record<string,
  Advisory[]> | null>;
  }
  Uses the npm bulk endpoint POST /-/npm/v1/security/advisories/bulk (the one
  npm audit uses; native fetch, zero deps). On any network/non-OK error it
  returns null — never throws, never blocks. Pure normalizer
  (normalizeAdvisories) split out for testing without network.

  3. New command: safe-add refresh

  Re-queries advisories for every ledgered dep (at its approvedVersion), writes
  updated cve snapshots back to the ledger via existing writeLedger. This is
  what you run on a cron/schedule. Offline → prints "couldn't verify, snapshots
  unchanged", exits 0.

  4. check — separate warnings channel

  runCheck stays pure/synchronous and keeps owning failures (missing entry,
  high-risk approval). A new async checkCveDrift(ledger, client) returns
  CveWarning[]:
  - queries live, diffs returned advisory IDs against each entry's stored
  cve.advisories
  - new ID present → warn "foo@1.2.3: new advisory GHSA-xxxx (high) since
  approval on "
  - offline → one "couldn't verify advisories" notice
  - never affects exit code. CI fails only on the existing violation rules.

  CLI prints warnings prominently after the violations block.

  5. Config

  Nothing required (always-warn needs no threshold). Optional later: a
  cveSeverityToWarn floor — I'd leave it out for YAGNI unless you want it.

  6. Testing

  Pure functions get unit tests with no network: normalizeAdvisories, the
  ID-diff logic, snapshot serialization, refresh ledger merge. A fake
  AdvisoryClient (returns canned data or null) covers drift-detected / no-drift
  / offline-fail-open paths. Matches the existing test style.

  ---
  Does this shape look right? Two specific calls I want your read on: (a) GHSA
  id as the stored identifier (most portable across DBs), and (b) dropping the
  config severity threshold for now (always-warn = no threshold needed).

⏺ Got it — that's a meaningful shift from "warn, never fail." A new CVE now
  fails the gate until a human re-approves, exactly like the existing high-risk
  model (refresh/observe = facts; human approvedBy = authorization). Let me
  revise the affected sections.

  1. Ledger shape (revised) — store the acknowledged advisory set

  interface CveSnapshot {
    acknowledged: { id: string; severity: "low"|"moderate"|"high"|"critical"
  }[]; // GHSA ids, human-signed-off
    acknowledgedBy: string | null;   // who re-approved (authorization)
    acknowledgedAt: string;          // ISO timestamp
  }
  // LedgerEntry gains:  cve?: CveSnapshot;
  We persist the set a human has acknowledged, not just what was observed. check
   queries live and compares against this.

  3. Re-approval mechanism (the new core)

  A new advisory ID present in the live query but not in cve.acknowledged = a
  dep that drifted. Clearing it requires a human, mirroring how high-risk works
  today (README: "a human adds approvedBy to its ledger entry"):

  safe-add reapprove <pkg> --approved-by "<name>"
  This re-queries, sets acknowledged to the current live advisory set, and
  records acknowledgedBy + acknowledgedAt. The diff is visible in the committed
  ledger / PR — the bypass stays impossible to hide. Running it is the only
  thing that updates acknowledged; a plain re-query never silently clears drift.

  4. check (revised) — drift is now a violation, with one exception

  check queries advisories live for each entry's approvedVersion, diffs against
  cve.acknowledged:
  - new unacknowledged advisory → violation, CI fails. Message: foo@1.2.3 gained
   GHSA-xxxx (high) since approval — re-approve: safe-add reapprove foo 
  --approved-by <you>.
  - fail-open on availability: offline / endpoint error → a "couldn't verify
  advisories" warning, exit unaffected. We only fail on a CVE we actually
  confirmed, never on a network blip.
  - resolved/disappeared advisories: not a violation.

  runCheck becomes async (or gains an async drift pass whose results merge into
  the violation list).

  ---
  Two decisions I'm making unless you object:

  1. Any new advisory triggers re-approval, regardless of severity (your "when
  there is a new CVE" — no severity threshold). I'll leave a cveSeverityFloor
  config as a future option, off by default.
  2. At safe-add time, if the version being added already carries advisories,
  they're recorded straight into cve.acknowledged (that add is already high-risk
   and needs approvedBy), so a clean install doesn't immediately fail its own

  The tool doesn't scan for CVEs — it tracks provenance: it records which
  advisories a human signed off on for the exact version they approved, then
  flags when that set drifts. "The version you approved later gained a CVE
  nobody acknowledged."

  The data: an acknowledged set per dependency

  Each ledger entry (.security/dependency-approvals.json) can carry an optional
  cve snapshot (src/ledger.ts):
  cve?: {
    acknowledged: { id: string; severity }[];  // GHSA ids a human signed off on
    acknowledgedBy: string;                     // who (authorization)
    acknowledgedAt: string;                     // when
  }
  acknowledged is the human-blessed advisory set. Everything keys off comparing
  live advisories against this set.

  The query: fail-open, by approved version (src/advisories.ts)

  NpmAdvisoryClient.fetchBulk POSTs { pkg: [approvedVersion] } to npm's bulk
  advisory endpoint (the one npm audit uses) and normalizes the response to { 
  pkg: [{id, severity}] }. Two design choices matter:
  - It queries the approved version from the ledger, not whatever range is in
  package.json — provenance is about what you approved.
  - It's fail-open: any error, non-OK status, or a 5s timeout → returns null
  (not an exception). A network blip can never block CI.

  The detection: detectDrift

  Pure function: for each live package, newAdvisories = live advisory ids not in
   that entry's acknowledged set. A missing cve field = empty acknowledged set
  (so every live advisory is "new"). Resolved advisories (acknowledged but no
  longer live) are simply ignored.

  The gate: runCheckWithCve (src/check-command.ts)

  This is what safe-add check runs in CI:
  1. Runs the existing pure runCheck first — keeps owning the base failures
  (missing ledger entry, high-risk needing approvedBy).
  2. Builds { name: [approvedVersion] } for every dep that has a ledger entry,
  calls fetchBulk.
  3. If null (couldn't verify): emits one WARN: Could not verify advisories…,
  adds no violations, exit code unaffected. Fail-open.
  4. Otherwise: each new advisory from detectDrift becomes a BLOCKED violation →
   CI exits 1, with the message telling you exactly what to run.

  So the only way check fails on CVEs is when it confirmed an advisory you never
   acknowledged.

  Clearing drift: reapprove (the human gate)

  safe-add reapprove <pkg> --approved-by "Jane"
  Re-queries advisories for the approved version and writes them into
  cve.acknowledged with the approver's name and timestamp (runReapprove in
  src/cli.ts). Crucially the opposite policy: it's fail-closed — if offline, it
  refuses to write, because we never record an acknowledgement we couldn't
  verify. This is the one action that updates the acknowledged set, so the
  bypass is always attributable to a named person and visible in the committed
  ledger diff.

  The asymmetry, summarized

  ┌───────────┬──────────────────┬──────────────────────────────────────────┐
  │           │ offline behavior │                   why                    │
  ├───────────┼──────────────────┼──────────────────────────────────────────┤
  │ check     │ warn, never fail │ a network blip shouldn't break your      │
  │           │                  │ build                                    │
  ├───────────┼──────────────────┼──────────────────────────────────────────┤
  │ reapprove │ error, don't     │ don't bless a CVE you couldn't actually  │
  │           │ write            │ look at                                  │
  └───────────┴──────────────────┴──────────────────────────────────────────┘

  Worth knowing

  - safe-add does not query advisories at install time (deliberate). So a
  package that already carries a CVE is BLOCKED on its first check until a human
   reapproves it — that's intentional: it forces a named human to sign off on a
  known-vulnerable add rather than auto-acknowledging silently.
  - YSNA_ADVISORY_URL overrides the endpoint (enterprise mirrors, or — as the
  tests do — pointing at an unreachable host to exercise the fail-open path
  deterministically offline).

⏺ CI is green on PR #6 (help/version). Now your question.

  Testing vouch in another local repo via npm link

  Two steps. First, in the vouch repo (build is required — the bin points at
  dist/):

  cd /Users/jan.pfajfr@rossum.ai/my/you-shall-not-add
  npm run build
  npm link

  npm link symlinks the package globally and puts the vouch binary on your PATH.

  Then, in your other repo:

  cd /path/to/your-other-repo
  npm link vouch

  Now run it there:

  vouch check
  vouch lodash
  vouch --help

  (Or skip step 2 entirely — after npm link in the vouch repo, the global vouch
  binary already works from anywhere; npm link vouch just also adds it to that
  repo's node_modules as if it were a dependency.)

  Important caveats

  - Rebuild after any change. The linked binary runs dist/, so re-run npm run 
  build in the vouch repo each time you edit source. (Or npx tsc --watch in one
  terminal.)
  - vouch actually installs packages in whatever repo you run it in (it shells
  out to your package manager) and writes .security/dependency-approvals.json
  there — so test in a throwaway repo, not something you care about.
  - The advisory calls hit the network; set YSNA_ADVISORY_URL=http://127.0.0.1:1
   to force the offline/fail-open path while testing.

⏺ That's the argument order biting you — and for a provenance tool, silently
  recording the wrong reason is genuinely bad, so it's worth being precise
  about.

  What happened

  You ran:
  vouch --force-with-reason esbuild "should be saved"
  A flag's value is the token immediately after it. So the parser read
  --force-with-reason's value as esbuild → reason: "esbuild", then took the next
   positional (esbuild) as the package, and silently dropped "should be saved".
  That's why the ledger shows "reason": "esbuild".

  The correct invocation

  Put the package first, the flag (with its value) after:
  vouch esbuild --force-with-reason "should be saved"
  That parses correctly — package esbuild, reason should be saved — and the
  upsert will overwrite the bad entry.

  The real problem

  This is the same arg-order fragility I hardened for reapprove during review,
  but the add command never got the same treatment — and worse, it fails
  silently (records a wrong reason) instead of erroring. On a tool whose whole
  job is honest attribution, that's a bug, not just a footgun.

  The fix I'd make:
  - Identify the package as the first positional that isn't the
  --force-with-reason value (mirroring the reapprove skip-set fix).
  - Reject ambiguous/extra arguments loudly — e.g. vouch --force-with-reason 
  esbuild "should be saved" should error (unexpected extra argument: "should be 
  saved") rather than quietly recording reason: "esbuild".

  So no invocation can silently write a reason you didn't intend.

❯ i was thinkg about => what if agent using cli for github or gitlab?           

⏺ Sharp question — it pokes right at the trust anchor of Phase 2, and the honest
   answer is: it exposes a real boundary the tool can't fully close by itself.

  The threat

  Phase 2 trusts "a permitted human approved the PR." But an agent with gh/glab
  authenticated can run:
  gh pr review <n> --approve        # or: glab mr approve
  GitHub/GitLab will record that as an approving review. vouch check sees an
  APPROVED review from a write-association account and passes. The tool 
  authenticates the account, not the humanness behind it. If an agent holds a
  credential that can approve, the gate is only as strong as that credential's
  custody.

  This is fundamental: no tool can distinguish a human from an agent acting with
   that human's token. The trust boundary is credential custody, which lives
  outside vouch.

  What already limits it (GitHub)

  - GitHub blocks self-approval — the PR author can't approve their own PR. So
  an agent that opened the PR can't approve it with the same account; the attack
   requires a second write-access identity. That's a meaningful bar, not
  nothing.
  - Our author_association filter already only counts OWNER/MEMBER/COLLABORATOR
  — a random external token doesn't qualify.

  What vouch could add (defense-in-depth, cheap)

  1. Exclude bot accounts — don't count reviews from *[bot] / type: "Bot" (so
  the Actions token or an automation account's approval never satisfies the
  gate).
  2. Reviewer ≠ author double-check — verify the approver isn't also a commit
  author on the PR (belt-and-suspenders over GitHub's own rule; meaningful on
  GitLab where it's weaker).
  3. allowedApprovers (already built) — pin to a known human set, so an agent
  needs that specific person's credential.
  4. A threat-model section in the docs — state plainly: verification trusts the
   platform's authentication of the reviewer account; keep approval credentials
  out of agent hands; use allowedApprovers + branch protection (required
  reviews, "require review from someone other than the last pusher").

  The GitLab wrinkle

  GitLab is weaker by default: author self-approval is allowed unless the
  project enables "Prevent approval by author." So the GitLab equivalent of this
   gate needs that setting on to match GitHub's baseline — worth documenting
  if/when we add a GitLab review client.

  The deeper framing

  This actually reinforces the layered model we designed: local signals are
  convenience, the platform review is the gate — but the platform review is only
   trustworthy if the agent and the approving human are different principals.
  vouch's honest role is to require the platform-authenticated act and to refuse
   to count its own/automation identities — not to claim it can tell who's
  really at the keyboard. The org keeps the human's approval credential away
  from the agent (which is exactly what AGENTS.md already tells the agent: don't
   self-authorize).

  Want me to harden Phase 2 with #1 + #2 (exclude bots, reviewer-≠-author) and
  add the threat-model doc section? It's a small, focused follow-up PR — and it
  meaningfully raises the bar against precisely the gh/glab self-approval path
  you're describing.
